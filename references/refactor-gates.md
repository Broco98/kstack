# 리팩터 관문

리팩터링은 **동작을 바꾸지 않고 구조만 바꾸는 일**이다. 여기 관문 여섯은 그 약속을 지켰는지, 그리고 바꾼 값어치가 있었는지를 증명한다.

**언제 읽나**: `kstack:refactor-plan`은 언제나 읽는다. spec이나 계획에 `종류: 리팩터링(동작 변경 없음)`이 적혀 있으면(리팩터 모드) `kstack:tickets` · `kstack:implement` · `kstack:inspect`도 함께 읽는다.

## 한눈에

| # | 관문 | 한 줄 | 누가 보나 |
|---|---|---|---|
| G1 | pin 먼저 | 구조를 건드리기 전에 지금 동작을 고정한다. 커밋 1번은 언제나 pin | `kstack:refactor-plan` · `kstack:tickets` · `kstack:implement` |
| G2 | 빼고 나서 더하기 | 커밋 순서는 pin → 빼기 → 모양 바꾸기 → 정리 | `kstack:refactor-plan` · `kstack:tickets` |
| G3 | 옛 API | 한 PR 안에서 green으로 끝나면 같은 PR에서 지운다. 아니면 expand–contract에 contract 티켓 필수 | `kstack:refactor-plan` · `kstack:tickets` |
| G4 | 가치 게이트 | 30초 테스트를 이전과 이후로 비교한다. 나아지지 않았으면 되돌리기를 제안한다 | `kstack:inspect` |
| G5 | 버그는 따로 | 리팩터링 중에 찾은 버그 · 빠진 기능은 별도 티켓으로 뗀다 | `kstack:implement` |
| G6 | 이름 바꾸기 확인 | 문자열 · 문서 · 역참조까지 파일을 하나씩 대조한다 | `kstack:implement` · `kstack:inspect` |

## G1. pin 먼저

pin(동작 고정)은 구조를 움직이기 전에 **지금 동작을 그대로 기록해 두는 장치**다. 구조를 바꾼 뒤에도 같은 기록이 나오면 동작이 바뀌지 않은 것이다.

- **고르는 법**: 셋 가운데 이 영역에 맞는 것을 쓴다.
  - **characterization test**(특성 테스트): 옳고 그름이 아니라 지금 동작 자체를 기록하는 테스트. 지금 나오는 출력을 그대로 기대값에 적는다.
  - **스냅샷**: 출력 전체를 파일로 떠 두고 비교한다.
  - **이전/이후 비교 하네스**: 같은 입력 묶음을 옛 코드와 새 코드에 넣고 출력을 diff한다.
- **어디서 무엇을 기록하나**를 적는다. seam(코드를 고치지 않고 동작을 끼워 넣거나 엿볼 수 있는 이음매) 하나를 골라, 그 자리에서 어떤 입력에 어떤 출력을 기록할지 정한다.
- **타입체크와 린트는 pin이 아니다.** 모양을 볼 뿐 동작을 기록하지 않는다.
- **커밋 1번은 언제나 pin이다.** pin이 지금 코드에서 green인 것을 확인한 뒤에 구조를 건드린다.
- 그 뒤 **모든 커밋에서 pin은 green**이어야 한다.

## G2. 빼고 나서 더하기

```
① pin → ② 빼기 → ③ 모양 바꾸기 → ④ 정리
```

- **② 빼기**: 죽은 코드, 호출자가 하나뿐인 래퍼, 겹치는 검증을 먼저 지운다. 줄어든 코드 위에서 모양을 바꾸면 옮길 것이 적다.
- **③ 모양 바꾸기**: 옮기기 · 합치기 · 쪼개기 · 이름 바꾸기.
- **④ 정리**: 남은 찌꺼기를 걷는다. 같은 폴더의 `deslop.md`를 여기서 쓴다.
- **«도움이 될지도 모르는» 정리는 되돌린다.** 읽는 부담을 실제로 줄이는 변경만 남긴다(G4).

## G3. 옛 API

물음 하나로 가른다.

> **호출자를 모두 옮기는 일이 한 PR 안에서 green으로 끝나나?**

- **끝난다** → 호출자를 모두 옮기고 **같은 PR에서 옛 API를 지운다.** shim(옛 인터페이스를 새 구현에 잇는 임시 어댑터)은 두지 않는다. 옛길과 새길이 함께 남지 않게 한다.
- **안 끝난다** → `kstack:tickets`의 expand–contract로 간다. 새 모양을 옆에 더하고(expand), 호출자를 묶음별로 옮기고, 옛 모양을 지운다(contract). 이때 **contract 티켓은 필수다.** contract 티켓이 없으면 옛길과 새길이 영영 함께 남는다.
- 판정과 근거를 계획에 적는다. 예: `G3: 호출자 <n>곳, 한 패키지 안 → 한 PR. 같은 PR에서 옛 API 삭제`.
- 옛 API가 저장소 밖에서도 쓰이면 지우는 일은 one-way 신호다(`door.md`).

## G4. 가치 게이트

리팩터링이 끝나면 **읽는 부담이 실제로 줄었는지** 판정한다. 읽는 부담은 두 축이다.

- **추적할 층**: 답을 찾으려고 건너야 하는 파일 · 함수 · 간접 호출
- **머리에 들 상태**: 동시에 기억해야 하는 값과, 그 값을 바꾸는 곳

**30초 테스트**: 이 영역의 핵심 상태 두세 개마다 두 물음에 30초 안에 답할 수 있나.

- «이 값은 **어디서 오나**?»
- «**무엇이** 이 값을 **바꾸나**?»

답이 한두 자리(`file:line`)를 짚는 것으로 끝나면 통과다. 층을 여러 번 건너야 하거나, 바꾸는 곳을 다 찾았다고 장담할 수 없으면 막힌 것이다.

1. 같은 물음을 이전 코드와 이후 코드에서 답한다. 답마다 `file:line`과 건넌 층을 적는다.
2. 아래 꼴의 표로 비교한다.
3. **어느 물음에서도 나아지지 않았으면 되돌리기를 제안한다.** 되돌릴지는 사람이 정한다.

| 물음 | 이전 | 이후 |
|---|---|---|
| `order.status`는 어디서 오나? | 층 셋을 건넌다. 30초 안에 못 답함 | `src/order/state.ts:20` 한 자리. 통과 |

이 물음은 `kstack:how` 함정 칸의 30초 질문과 같다. 리팩터링이 `kstack:how`에서 막힌 자리에서 시작했다면 그때의 물음을 그대로 다시 쓴다.

## G5. 버그는 따로

- 리팩터링 중에 버그나 빠진 기능을 찾으면 **이 작업에서 고치지 않고 떼어 낸다.** 별도 티켓에 무엇이 · 어디서(`file:line`) · 어떻게 재현되는지를 적는다.
- **왜**: pin은 지금 동작을 그대로 기록한다. 버그도 함께 기록돼 있다. 버그를 고치면 pin이 바뀌고, 그 순간 «동작이 바뀌지 않았다»는 증명이 무너진다.
- 구조 변경을 고정된 동작 기준으로 **먼저 출하하고**, 버그는 그 위에서 고친다.

## G6. 이름 바꾸기 확인

- 이름을 바꾸면 컴파일러가 잡지 못하는 자리에서 놓치기 쉽다. 문자열 안의 이름(`obj["oldName"]`, 이벤트 이름, 직렬화 키), 문서와 주석, 설정 파일, 역참조(로그 검색어, 다른 저장소)가 그렇다.
- 옛 이름으로 저장소 전체를 검색하고, **걸린 파일을 하나씩 열어 대조한다.** 남긴 자리는 이유를 적는다.

## 단계별로 읽는 법

- **`kstack:refactor-plan`**: G1의 pin을 커밋 1번으로 넣는다. 커밋 순서를 G2대로 짠다. 옛 API가 있으면 G3 판정을 적는다. 이슈 템플릿의 `Testing Decisions`에 pin 방식과 G4의 30초 질문을 적는다.
- **`kstack:tickets`**: 첫 티켓이 pin이다. G3에서 expand–contract로 가면 contract 티켓을 반드시 둔다.
- **`kstack:implement`**: 티켓의 증명 명령이 곧 pin 테스트다. 커밋마다 green을 유지한다. G5에 걸리면 별도 티켓으로 뗀다. 이름을 바꿨으면 G6을 거친다.
- **`kstack:inspect`**: Correctness 축이 **동등성 증명**으로 바뀐다. 이전/이후 출력 diff나 기록해 둔 기준선 재생을 쓴다. 여기에 G4 가치 게이트 결과를 덧붙인다. Spec 축은 «동작이 바뀌지 않았나»를 본다.
- **`kstack:pr`**: Evidence는 pin 테스트다. Door는 대개 two-way다.
