# ADR 형식

ADR은 `docs/adr/`에 두고 순번을 매긴다. `0001-slug.md`, `0002-slug.md` 식이다.

`docs/adr/` 디렉터리는 필요할 때 만든다. 첫 ADR이 필요할 때만 만든다.

## 템플릿

```md
# {결정의 짧은 제목}

{1~3문장: 맥락이 무엇이고, 무엇을 결정했고, 왜 그랬는가.}
```

이게 전부다. ADR은 한 문단이어도 된다. 가치는 칸을 채우는 데 있지 않고, 결정이 내려졌다는 *사실*과 *이유*를 남기는 데 있다.

## 선택 항목

진짜 가치를 더할 때만 넣는다. 대부분의 ADR에는 필요 없다.

- **Status** frontmatter(`proposed | accepted | deprecated | superseded by ADR-NNNN`): 결정을 다시 검토할 때 유용하다
- **Considered Options**: 버린 대안을 기억해 둘 가치가 있을 때만
- **Consequences**: 뻔하지 않은 하류 영향을 짚어야 할 때만

## 번호 매기기

`docs/adr/`에서 가장 큰 기존 번호를 찾아 하나 올린다.

## ADR을 제안할 때

세 가지가 모두 참이어야 한다.

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 의미 있게 크다
2. **맥락 없이는 놀랍다**: 훗날 코드를 보는 사람이 "대체 왜 이렇게 했지?" 하고 의아해할 것이다
3. **진짜 트레이드오프의 결과다**: 실제로 대안이 있었고, 특정한 이유로 하나를 골랐다

결정이 되돌리기 쉽다면 건너뛴다. 그냥 되돌리면 된다. 놀랍지 않다면 아무도 이유를 궁금해하지 않는다. 진짜 대안이 없었다면 "뻔한 걸 했다" 외에 기록할 것이 없다.

### 해당하는 것

- **아키텍처의 모양.** "모노레포를 쓴다." "쓰기 모델은 이벤트 소싱이고, 읽기 모델은 Postgres로 투영한다."
- **컨텍스트 사이의 통합 패턴.** "Ordering과 Billing은 동기 HTTP가 아니라 도메인 이벤트로 소통한다."
- **락인이 따르는 기술 선택.** 데이터베이스, 메시지 버스, 인증 제공자, 배포 대상. 모든 라이브러리가 아니라, 바꾸는 데 한 분기가 걸릴 것들만.
- **경계와 범위 결정.** "고객 데이터는 Customer 컨텍스트가 소유하고, 다른 컨텍스트는 ID로만 참조한다." 명시적인 "아니오"는 "예"만큼 가치 있다.
- **뻔한 길에서 의도적으로 벗어난 선택.** "X 때문에 ORM 대신 수작업 SQL을 쓴다." 합리적인 독자라면 반대로 가정할 모든 것. 의도한 것을 다음 엔지니어가 "고치는" 일을 막아 준다.
- **코드에 보이지 않는 제약.** "컴플라이언스 요건 때문에 AWS를 쓸 수 없다." "파트너 API 계약 때문에 응답 시간은 200ms 아래여야 한다."
- **거절의 이유가 뻔하지 않은 버린 대안.** GraphQL을 검토했다가 미묘한 이유로 REST를 골랐다면 기록한다. 그러지 않으면 6개월 뒤 누군가 또 GraphQL을 제안한다.
