# Domain Modeling

설계하면서 프로젝트의 도메인 모델을 적극적으로 쌓고 다듬는다. 이것은 *능동적인* 규율이다. 용어에 이의를 제기하고, 엣지 케이스 시나리오를 지어내고, 용어집과 결정을 굳어지는 즉시 적는다. (어휘를 얻으려고 `GLOSSARY.md`를 *읽기만* 하는 것은 이 스킬이 아니다. 그건 어느 스킬이든 하는 한 줄짜리 습관이다. 이 스킬은 모델을 읽는 데 그치지 않고 *바꿀* 때 쓴다.)

## 파일 구조

대부분의 저장소는 컨텍스트가 하나다.

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `GLOSSARY-MAP.md`가 있으면 그 저장소는 컨텍스트가 여럿이다. 맵이 각 컨텍스트가 어디 있는지 알려 준다.

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전체 결정
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 컨텍스트별 결정
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

파일은 필요할 때만 만든다. 쓸 내용이 생겼을 때 만든다. `GLOSSARY.md`가 없으면 첫 용어가 정리될 때 만든다. `docs/adr/`가 없으면 첫 ADR이 필요할 때 만든다.

## 세션 중에

### 용어집에 대조해 이의를 제기한다

사용자가 `GLOSSARY.md`의 기존 언어와 어긋나는 용어를 쓰면 바로 짚는다. "용어집은 'cancellation'을 X로 정의하는데, Y를 말씀하시는 것 같습니다. 어느 쪽인가요?"

### 흐릿한 말을 날카롭게 한다

사용자가 모호하거나 뜻이 겹치는 용어를 쓰면 정확한 표준 용어를 제안한다. "'account'라고 하셨는데, Customer를 말씀하시나요, User를 말씀하시나요? 둘은 다른 것입니다."

### 구체적인 시나리오를 논의한다

도메인 관계를 논의할 때는 구체적인 시나리오로 압박 테스트한다. 엣지 케이스를 건드리는 시나리오를 지어내서, 개념 사이의 경계를 사용자가 정확히 말하게 만든다.

### 코드와 교차 확인한다

사용자가 어떤 것의 동작 방식을 말하면 코드가 그와 맞는지 확인한다. 모순을 찾으면 드러낸다. "코드는 Order 전체를 취소하는데, 방금 부분 취소가 가능하다고 하셨습니다. 어느 쪽이 맞나요?"

### GLOSSARY.md를 그 자리에서 고친다

용어가 정리되면 바로 그 자리에서 `GLOSSARY.md`를 고친다. 모아 두었다 한꺼번에 하지 않고 일어나는 대로 적는다. 형식은 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)를 따른다.

`GLOSSARY.md`에는 구현 세부가 전혀 없어야 한다. `GLOSSARY.md`를 스펙이나 메모장, 구현 결정의 보관소로 쓰지 않는다. 그것은 용어집이고, 용어집일 뿐이다.

### ADR은 아껴서 제안한다

세 가지가 모두 참일 때만 ADR 작성을 제안한다.

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 의미 있게 크다
2. **맥락 없이는 놀랍다**: 훗날 읽는 사람이 "왜 이렇게 했지?" 하고 의아해할 것이다
3. **진짜 트레이드오프의 결과다**: 실제로 대안이 있었고, 특정한 이유로 하나를 골랐다

셋 중 하나라도 빠지면 ADR은 건너뛴다. 형식은 [ADR-FORMAT.md](./ADR-FORMAT.md)를 따른다.
