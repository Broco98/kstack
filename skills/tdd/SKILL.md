# Test-Driven Development

TDD는 red → green 루프다. 이 스킬은 그 루프가 남길 만한 테스트를 낳게 하는 레퍼런스다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴, 루프의 규칙을 다룬다. 모든 절이 매 사이클에 적용된다. 루프 전과 루프 중에 참고하고, 끝난 뒤에 보지 않는다.

코드베이스를 탐색할 때 `GLOSSARY.md`가 있으면 읽어서 테스트 이름과 인터페이스 어휘를 프로젝트의 도메인 언어에 맞춘다. 손대는 영역의 ADR도 존중한다.

## 좋은 테스트란

테스트는 구현 세부가 아니라 공개 인터페이스를 통해 동작을 검증한다. 코드는 통째로 바뀌어도 테스트는 바뀌지 않아야 한다. 좋은 테스트는 명세처럼 읽힌다. "user can checkout with valid cart"는 어떤 능력이 있는지 정확히 알려 주고, 내부 구조를 신경 쓰지 않으니 리팩터링에도 살아남는다.

예시는 [tests.md](tests.md), 모킹 지침은 [mocking.md](mocking.md)를 본다.

## Seam: 테스트를 두는 곳

**seam**(이음매)은 테스트하는 공개 경계다. 안쪽을 건드리지 않고 동작을 관찰하는 인터페이스다. 테스트는 seam에 두고, 내부를 겨냥하지 않는다.

**미리 합의한 seam에서만 테스트한다.** 테스트를 쓰기 전에, 테스트 대상 seam을 적어 두고 사용자와 확인한다. 확인하지 않은 seam에는 테스트를 쓰지 않는다. 모든 것을 테스트할 수는 없다. seam을 먼저 합의하는 것은 테스트 노력이 모든 엣지 케이스가 아니라 핵심 경로와 복잡한 로직에 쏠리게 하는 방법이다.

이렇게 묻는다. "공개 인터페이스가 무엇이고, 어떤 seam을 테스트해야 할까요?" 제안하는 seam마다 무엇을 잡아내고 무엇을 놓치는지 한 줄씩 적는다.

인터페이스의 모양 자체가 문제일 때(모듈이 얼마나 깊은지, seam이 어디에 속하는지, 인터페이스가 무엇을 드러내야 하는지)는 Skill tool로 `kstack:codebase-design`을 불러 어휘를 얻는다. 그것은 module, interface, depth, seam, adapter, leverage, locality 용어의 공용 출처이고, 참고할 레퍼런스이지 돌리는 세션이 아니다.

## 안티패턴

- **구현에 결합된 테스트**: 내부 협력자를 모킹하고, private 메서드를 테스트하고, 우회 경로로 검증한다(인터페이스를 쓰지 않고 데이터베이스를 직접 조회하는 식). 신호는 동작이 그대로인데 리팩터링하면 테스트가 깨지는 것이다.
- **동어반복 테스트(tautological)**: 단언이 코드가 계산하는 방식 그대로 기대값을 다시 계산한다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 손수 만든 스냅샷, 자기 자신과 같다고 단언하는 상수). 구성상 통과하고 코드와 어긋날 수 없다. 기대값은 독립된 진실의 원천에서 와야 한다. 검증된 리터럴, 손으로 푼 예시, 스펙이다.
- **수평 슬라이싱(horizontal slicing)**: 테스트를 전부 먼저 쓰고 구현을 전부 나중에 쓰는 것. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증한다. 사용자에게 보이는 동작이 아니라 사물의 _모양_을 테스트하고, 실제 변화에 둔감해지며, 구현을 이해하기도 전에 테스트 구조에 매이게 된다. 대신 **수직 슬라이스(vertical slices)**로 일한다. 테스트 하나 → 구현 하나 → 반복. 각 테스트가 직전 사이클에서 배운 것에 반응하는 **tracer bullet**(예광탄)이 된다.

## 루프의 규칙

- **green보다 red가 먼저.** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼만 코드를 쓴다. 앞으로 올 테스트를 미리 짐작하거나 추측성 기능을 더하지 않는다.
- **한 번에 한 슬라이스.** 사이클마다 seam 하나, 테스트 하나, 최소 구현 하나.
- **리팩터링은 루프에 속하지 않는다.** 리팩터링은 red → green 구현 사이클이 아니라 리뷰 단계(`kstack:inspect` 스킬 참고)의 일이다.
