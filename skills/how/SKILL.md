# how

독자는 **질문한 사용자 본인**이다. 목표는 지금 하려는 일에 필요한 만큼 코드의 동작을 사용자 머리에 넣는 것이다. 오래 남길 학습은 `/kstack:teach`의 몫이다.

이 스킬은 설명만 한다. 코드를 고치는 일은 사용자가 정한 뒤에 한다.

## 1. 대상과 묻는 이유

- 인자가 대상이다. 없으면 대화에서 지금 다루던 것.
- **묻는 이유를 대화에서 읽는다.** 이유에 따라 **먼저 가져갈 것 두세 개**를 고른다. 답 전체가 이것을 중심으로 선다.

  | 묻는 이유 | 먼저 가져갈 것 |
  |---|---|
  | 고치려 한다 | 바꿀 자리, 그 자리를 부르는 쪽, 깨지기 쉬운 약속(불변식) |
  | 리뷰한다 | 바뀐 부분이 흐름의 어디에 끼나, 경계 조건 |
  | 디버깅 중이다 | 증상이 나는 경로, 상태가 바뀌는 자리, 갈림길 |
  | 처음 본다 | 입구, 큰 덩어리 몇 개, 데이터가 흐르는 방향 |

- 이유가 보이지 않으면 «처음 본다»로 두고, 그 가정을 개요 첫 줄에 밝힌다.

## 2. 탐색 — 애매하면 단순 쪽으로

```
질문 ─┬─ 단순 (모듈 하나 · 함수 하나) ──→ 설명자 1명이 탐색과 설명을 한 번에
      │
      └─ 복잡 (여러 파일 · 서비스에 걸침) ──→ 관점 2~4개로 쪼개 동시에
              ├ 탐색자 A (Explore) ─┐  각자 file:line 사실을 모은다
              ├ 탐색자 B (Explore) ─┼─→ 설명자 (general-purpose, sonnet)
              └ 탐색자 C (Explore) ─┘  어긋나면 코드를 직접 확인한다
```

**애매하면 단순 쪽으로 간다.** 단순으로 읽다가 흐름이 서비스나 여러 모듈을 건너는 것이 보이면 그때 복잡으로 바꾼다.

### 단순

설명자는 메인 에이전트 자신이다. 코드를 직접 읽고 §3 골격으로 바로 답한다.

### 복잡

1. **관점을 2~4개 고른다.** 관점은 질문을 서로 겹치지 않게 자른 조각이다. 예:
   - **입구에서 출구까지**: 요청이나 이벤트가 들어와 결과가 나가기까지 거치는 함수
   - **상태와 저장**: 데이터가 어디에 머물고 누가 바꾸나
   - **경계**: 외부 호출 · 설정 · 에러 처리
   - **묻는 이유가 짚는 자리**: 고치려는 곳의 호출자, 디버깅 중인 증상의 경로
2. **탐색자를 한 메시지에서 동시에 띄운다.** Agent tool, `subagent_type: "Explore"`, 관점마다 하나. 탐색자는 위치를 찾고 사실을 모으기만 한다. 브리프는 이렇다.

   ```
   질문: <사용자의 질문>
   관점: <이 탐색자가 맡은 관점>
   범위: <폴더 · 모듈>
   할 일: 이 관점에 닿는 코드의 위치를 찾고, 사실을 `file:line — 한 줄 사실` 꼴로 모은다.
   보고: 사실 목록만 낸다. 해석과 설명은 설명자가 한다.
   ```

3. **설명자를 띄운다.** Agent tool, `subagent_type: "general-purpose"`, `model: "sonnet"`. 브리프에 질문, 묻는 이유와 먼저 가져갈 것, 탐색 결과 전부를 넣는다. 그리고 «`<이 SKILL.md의 절대 경로>`의 §3~§8을 따라 답을 쓴다»고 적는다.
   - **탐색 결과끼리 어긋나면 설명자가 코드를 직접 열어 확인하고**, 맞는 쪽만 쓴다.
4. 설명자의 답을 §8 점검에 통과시킨 뒤 사용자에게 전한다. 걸린 곳이 있으면 고쳐서 전한다.

## 3. 답의 골격 — 다섯 칸

칸 이름과 순서는 **아래 그대로** 쓴다. 검사 스크립트가 이 이름과 순서를 본다. 쓸모없는 칸은 빼고, 남은 칸의 순서는 지킨다.

### `## 개요`

1~2문단. 이것만 읽고 더 읽을지 정할 수 있게 쓴다. §1에서 고른 «먼저 가져갈 것»이 여기서 먼저 나온다.

### `## 핵심 개념`

흐름을 읽기 전에 알아야 할 이름들. 타입 · 상태 · 도메인 용어를 하나에 한두 줄로. 저장소에 `GLOSSARY.md`가 있으면 그 말을 쓴다.

### `## 동작 흐름`

**가장 길게 쓴다.** 무엇이 시작하나 → 데이터가 어디로 가나 → 어디서 갈리나 → 어디서 끝나나. 단계마다 `file:line`을 붙인다. 그림은 §4대로 한 장씩 쌓는다.

### `## 어디에 있나`

파일 지도. 얕은 트리에 파일마다 맡은 일을 한 줄로 적는다.

```
src/cart/
├── load.ts      # 저장소에서 장바구니를 읽는다
├── total.ts     # 합계를 계산한다
└── sync.ts      # 서버와 맞춘다
```

### `## 함정`

놓치기 쉬운 것을 적는다. 숨은 부수 효과, 순서에 기대는 코드, 같은 이름 다른 뜻 같은 것이다. 그리고 **30초 질문**(§6)을 둔다. 30초 질문이 있으니 이 칸은 거의 빠지지 않는다. 다룬 코드에 상태가 없을 때만 뺀다.

---

**작은 답을 먼저 하고 멈춘다.** 칸마다 묻는 이유에 필요한 만큼만 쓴다. 답은 `## 함정`에서 끝난다. 더 깊이는 사용자가 물을 때 간다. 이어지는 물음에는 칸 없이 그 물음에만 답하고, 그림은 앞 그림을 다시 그리면서 하나를 더한다.

말투는 해요체다. 전문 용어는 처음 나올 때 괄호로 한 줄 풀이를 붙인다.

## 4. 그림 — 한 장씩 쌓는다

- 터미널에서는 **코드 블록 안에 ASCII로** 그린다. 터미널은 mermaid를 그리지 못한다.
- 첫 그림은 둘로 시작한다(A → B). 다음 그림은 같은 그림을 다시 그리면서 C를 더한다. **한 장에 새 요소는 하나나 둘.**
- 한 장에 다 넣은 그림은 참고 자료이지 설명이 아니다. 전체 그림은 쌓아 올린 끝에 나온다.
- 그림 바로 옆에, 그 그림이 보여 주는 것을 짧게 적는다.

```
요청 ──→ router
```

```
요청 ──→ router ──→ handler
```

```
요청 ──→ router ──→ handler ──→ cache
                                  │ 없으면
                                  ▼
                                  DB
```

## 5. 증거와 확신도

- **동작 흐름은 사다리 ②(`file:line`) 이상으로만 단정한다.** 기준은 `references/evidence-ladder.md`다. 짚지 못한 단계는 «확인 못 함»이라고 적는다.
- **의도**(왜 이렇게 만들었나)를 말하게 되면 진술마다 확신도 딱지를 붙인다. 기준은 `references/confidence-tiers.md`다. «~때문이다», «~하려고 설계됐다»는 인용이 바로 옆에 있을 때만 쓴다.
- **깊은 «왜»는 `/why`로 넘긴다.** 의도가 질문의 중심이 되면, 의도는 딱지 붙인 한 줄로 두고 `/why <대상>`을 권한다.

## 6. 함정 칸의 30초 질문

1. 묻는 이유와 닿는 **핵심 상태 두세 개**를 고른다.
2. 상태마다 두 물음에 답한다. «**어디서 오나?**» «**무엇이 바꾸나?**» 답은 `file:line`으로 짚는다.
3. **30초 안에 답이 안 나오는 곳**에 `리팩터링 후보`라고 적고, 왜 막혔는지 한 줄 붙인다. 답이 한두 자리를 짚는 것으로 끝나면 통과다. 층을 여러 번 건너야 하거나, 바꾸는 곳을 다 찾았다고 장담할 수 없으면 막힌 것이다.
4. `리팩터링 후보`가 하나라도 있으면 함정 칸 끝에 다음 걸음을 한 줄 둔다. `/kstack:improve-codebase-architecture <그 자리>`로 이 자리를 리팩터링 후보로 넘길 수 있다고 적는다.

```markdown
**30초 질문**
- `cart.total`은 어디서 오나요? → `computeTotal()` (`src/cart/total.ts:18`). 통과
- `cart.total`은 무엇이 바꾸나요? → `applyCoupon` (`src/cart/coupon.ts:40`), `syncFromServer` (`src/cart/sync.ts:72`), 그리고 이벤트 버스를 두 번 건너는 웹소켓 핸들러. 바꾸는 곳을 다 찾았는지 장담할 수 없어요. `리팩터링 후보`

→ `/kstack:improve-codebase-architecture src/cart`로 이 자리를 리팩터링 후보로 넘길 수 있어요.
```

리팩터링이 끝나면 같은 물음으로 나아졌는지 판정한다(`references/refactor-gates.md` G4). 그래서 물음은 나중에 그대로 다시 물을 수 있게 적는다.

## 7. 퀴즈 없이 끝낸다

**답은 설명으로 끝난다.** 확인 퀴즈, 되말해 보라는 요청, «이해되셨나요?» 같은 마무리 질문은 붙이지 않는다.

이것은 지금 작업을 위한 이해다. 술술 읽혔다는 느낌(fluency)은 오래 남는 기억과 다르다. 사용자가 이 영역을 오래 맡아 제대로 익히고 싶다고 하면 `/kstack:teach`를 권한다.

## 8. 답하기 전 점검 — 세어서 0

- **① 다섯 칸 밖의 이름이거나 순서가 어긋난 `##` 칸 0**
- **② `file:line` 없이 단정한 흐름 단계 0**: 짚었거나 «확인 못 함».
- **③ 딱지 없는 의도 진술 0**
- **④ 첫 장부터 전체를 다 넣은 그림 0**
- **⑤ 답이 없는 30초 질문 0**: 답했거나 `리팩터링 후보`.
