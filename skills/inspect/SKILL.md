Standards(이 저장소가 문서로 정한 코딩 표준을 따르나), Spec(원천 이슈 · spec이 요구한 대로인가), Correctness(다른 곳 · 빌드와 실행 · 보안을 깨나. 재현 명령으로 확인한 것만 남긴다). 세 리뷰를 병렬 하위 에이전트로 돌려 나란히 보고한다. 브랜치 · PR · 작업 중인 변경을 리뷰하려 하거나 «X 이후를 리뷰해 줘(review since X)»라고 할 때 사용한다."

> Claude Code가 아닌 에이전트에서는 도구 · 모델 이름을 `references/agents.md`로 바꿔 읽는다.

고정점과 `HEAD` 사이 diff를 세 축으로 리뷰한다. 고정점은 사용자가 준다.

- **Standards**: 코드가 이 저장소가 문서로 정한 코딩 표준을 따르나?
- **Spec**: 코드가 원천 이슈 / spec을 충실히 구현하나?
- **Correctness**: 이 diff가 다른 곳 · 개발 환경 · 보안을 깨나? 재현 명령으로 확인한 것만 지적으로 남는다.

세 축은 서로의 context를 오염시키지 않도록 **병렬 하위 에이전트**로 돌리고, 이 스킬이 결과를 모은다.

이슈 트래커는 이미 주어졌어야 한다. 없으면 사용자에게 `/kstack:setup`을 실행하라고 알린다.

## 절차

### 1. 고정점을 정한다

사용자가 말한 것이 고정점이다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 말하지 않았으면 묻는다.

diff 명령을 한 번 정해 둔다. `git diff <fixed-point>...HEAD`다(점 셋. merge-base와 비교한다). 커밋 목록도 `git log <fixed-point>..HEAD --oneline`으로 적어 둔다.

더 나가기 전에 고정점이 풀리는지(`git rev-parse <fixed-point>`), diff가 비어 있지 않은지 확인한다. 잘못된 ref나 빈 diff는 병렬 하위 에이전트들 안이 아니라 **여기서** 실패해야 한다.

### 2. spec 출처를 찾는다

원천 spec을 이 순서로 찾는다.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). 트래커 문서의 workflow로 가져온다.
2. 사용자가 인자로 준 경로.
3. `docs/`, `specs/`, `.scratch/` 아래에서 브랜치 이름이나 기능과 맞는 spec 파일.
4. 아무것도 찾지 못하면 사용자에게 spec이 어디 있는지 묻는다. 없다고 하면 **Spec** 하위 에이전트는 건너뛰고 «spec 없음»으로 보고한다.

찾은 spec에 `종류: 리팩터링(동작 변경 없음)`이 적혀 있으면 이 리뷰는 **리팩터 모드**다(맨 아래 «리팩터 모드»).

### 3. 표준 출처를 찾는다

저장소에서 코드를 어떻게 써야 하는지 문서로 적은 파일을 모두 찾는다. `CODING_STANDARDS.md`나 `CONTRIBUTING.md`가 있으면 반드시 목록에 넣는다.

저장소가 무엇을 문서로 적었든, Standards 축은 그 위에 언제나 아래 **smell baseline**(냄새 기준선)을 지닌다. Fowler 코드 냄새(_Refactoring_, 3장)에서 고른 고정된 묶음이고, 저장소가 아무것도 문서로 적지 않았어도 적용된다. 두 규칙이 이것을 묶는다.

- **저장소가 우선한다.** 문서화된 저장소 표준이 언제나 이긴다. baseline이 짚을 것을 저장소 표준이 인정하면 그 smell은 내린다.
- **언제나 판단의 문제다.** smell마다 딱지를 붙인 휴리스틱(«Feature Envy일 수 있음»)이지 단단한 위반이 아니다. 여기의 다른 표준처럼, 도구가 이미 강제하는 것은 건너뛴다.

smell마다 *무엇인가* → *어떻게 고치나* 순으로 읽는다. diff에 대어 본다.

- **Mysterious Name**: 이름이 하는 일이나 담은 것을 드러내지 않는 함수 · 변수 · 타입. → 이름을 바꾼다. 정직한 이름이 떠오르지 않으면 설계가 흐린 것이다.
- **Duplicated Code**: 같은 로직 모양이 변경 안의 hunk나 파일 여러 곳에 나온다. → 공통 모양을 뽑아내고 양쪽에서 부른다.
- **Feature Envy**: 자기 데이터보다 다른 객체의 데이터에 더 손을 뻗는 메서드. → 메서드를 그것이 탐내는 데이터 쪽으로 옮긴다.
- **Data Clumps**: 같은 필드나 매개변수 몇 개가 늘 붙어 다닌다(태어나고 싶어 하는 타입이다). → 한 타입으로 묶어 그것을 넘긴다.
- **Primitive Obsession**: 자기 타입을 가질 만한 도메인 개념을 원시 값이나 문자열이 대신한다. → 그 개념에 작은 타입을 준다.
- **Repeated Switches**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 곳곳에 되풀이된다. → 다형성으로 바꾸거나, 두 자리가 함께 쓰는 map 하나로 바꾼다.
- **Shotgun Surgery**: 논리적 변경 하나가 diff 속 여러 파일에 흩어진 수정을 강요한다. → 함께 바뀌는 것을 한 모듈로 모은다.
- **Divergent Change**: 파일이나 모듈 하나가 서로 무관한 여러 이유로 고쳐진다. → 모듈마다 한 가지 이유로만 바뀌도록 나눈다.
- **Speculative Generality**: spec에 없는 필요를 위해 더한 추상화 · 매개변수 · 훅. → 지운다. 진짜 필요가 보일 때까지 도로 인라인한다.
- **Message Chains**: 호출자가 기대면 안 되는 긴 `a.b().c().d()` 탐색. → 첫 객체의 메서드 하나 뒤로 그 길을 숨긴다.
- **Middle Man**: 대부분 그저 넘겨주기만 하는 클래스나 함수. → 잘라 내고 진짜 대상을 바로 부른다.
- **Refused Bequest**: 물려받은 것 대부분을 무시하거나 덮어쓰는 하위 클래스나 구현체. → 상속을 버리고 합성을 쓴다.

### 4. Door를 정하고 하위 에이전트를 함께 띄운다

먼저 이 diff의 **Door**(되돌릴 수 있는 two-way인가, 되돌릴 수 없는 one-way인가)를 `references/door.md`로 판정한다. spec의 Implementation Decisions에 Door 표시가 있으면 그것도 근거로 쓴다. Correctness 리뷰어의 수와 모델은 `door.md`의 강도 표를 따른다. two-way면 1명(opus)이고, one-way면 서로 모르게 띄우는 적대 리뷰어 2명(opus 1명 + sonnet 1명)이다.

하위 에이전트 호출을 **모두 한 메시지에서 함께, foreground로** 보내고 돌아온 보고를 모은다. Standards와 Spec은 사실 대조라 general-purpose(sonnet)로 띄운다. Correctness는 같은 메시지에서 위의 수대로 general-purpose로 띄운다.

**Standards 하위 에이전트 프롬프트**에 넣을 것:

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록, **그리고 3단계의 smell baseline 전문**(하위 에이전트는 달리 그것을 볼 길이 없다).
- 브리프: «파일/hunk별로 보고한다. (a) diff가 문서화된 표준을 어긴 모든 자리. 그 표준을 인용한다(파일 + 규칙). (b) 눈에 띈 baseline smell. 이름을 대고 hunk를 인용한다. 단단한 위반과 판단의 문제를 가른다. 문서화된 표준 위반은 단단할 수 있지만 baseline smell은 언제나 판단의 문제이고, 문서화된 저장소 표준이 baseline보다 우선한다. 도구가 강제하는 것은 건너뛴다. 400단어 이내.»

**Spec 하위 에이전트 프롬프트**에 넣을 것:

- diff 명령과 커밋 목록.
- spec의 경로 또는 가져온 내용.
- 브리프: «보고한다. (a) spec이 요구했는데 빠졌거나 덜 된 요구사항. (b) diff에 있지만 요구하지 않은 동작(scope creep). (c) 구현된 듯하지만 구현이 틀려 보이는 요구사항. 지적마다 spec의 해당 줄을 인용한다. 400단어 이내.»

spec이 없으면 Spec 하위 에이전트는 건너뛰고 최종 보고에 그렇게 적는다.

**Correctness 하위 에이전트 프롬프트**에 넣을 것:

- diff 명령과 커밋 목록.
- 증거 사다리 `references/evidence-ladder.md`의 절대 경로(이 스킬 폴더 기준).
- 브리프: «이 diff가 무엇을 깨는지 찾는다. 볼 것은 넷이다. (1) 다른 곳을 깨나: 호출자, wire format, DB column, 세 단계 아래의 코드. (2) 개발 환경을 깨나: 빌드, 실행. (3) 보안 구멍이 있나. (4) feature flag가 새나. 지적마다 **재현 명령, 그 명령의 실제 출력, 의도대로라면 나와야 할 출력**을 낸다(사다리 ④ 이상). 돌려 보지 못한 것은 지적이 아니다. «의심» 목록에 따로 둔다. 저장소 파일은 고치지 않는다. 재현에 스크립트가 필요하면 저장소 밖 임시 폴더에 둔다.»

one-way면 같은 프롬프트로 두 리뷰어를 띄운다.

### 5. Correctness 지적을 다시 돌려 본다

Correctness 보고는 그대로 옮기지 않는다. 지적마다 재현 명령을 **직접 다시 돌린다.**

- 보고된 출력이 다시 나오면 확인된 지적이다. `## Correctness`에 남긴다.
- 다시 나오지 않으면 «의심»으로 내리고, 다시 돌린 출력을 함께 적는다.
- 명령이 저장소 밖을 바꾸거나 되돌릴 수 없는 일을 하면 돌리지 않고 «의심»으로 둔다.
- Correctness 안에서 근본 원인이 같은 지적은 하나로 합친다. 리뷰어가 둘이면 두 보고의 지적도 이렇게 합친다.

### 6. 모은다

세 보고를 `## Standards` · `## Spec` · `## Correctness` 제목 아래에 따로 둔다. Standards와 Spec은 그대로 또는 가볍게 다듬어 옮기고, Correctness는 5단계에서 확인된 것만 옮긴다. 축끼리 지적을 합치거나 순위를 다시 매기지 **않는다.** 세 축은 일부러 떼어 놓은 것이다(«왜 축을 나누나» 참고).

«의심»은 그 뒤 `## 의심` 제목 아래 따로 둔다. 지적 수에 넣지 않는다.

한 줄 요약으로 끝낸다. 축마다 지적 수와 _각 축 안에서_ 가장 나쁜 지적(있다면), 그리고 의심 수다. 축을 건너 하나의 승자를 고르지 않는다. 그것이 바로 축을 나눠서 막으려는 재순위다.

## 리팩터 모드

2단계에서 찾은 spec에 `종류: 리팩터링(동작 변경 없음)`이 있으면 `references/refactor-gates.md`를 함께 따른다. Correctness 하위 에이전트에게도 이 파일의 절대 경로와 spec의 Testing Decisions를 넘긴다.

- **Correctness**는 **동등성 증명**으로 바뀐다. 브리프의 «볼 것 넷» 대신, 고정점과 `HEAD`의 동작이 같음을 보인다. 이전/이후 출력 diff를 내거나, 기록해 둔 기준선을 재생한다. 증명마다 명령과 출력을 내고 메인이 다시 돌려 확인하는 규칙은 그대로다. 여기에 **G4 가치 게이트** 결과를 덧붙인다. spec의 Testing Decisions에 적힌 30초 질문을 이전 코드와 이후 코드에 똑같이 던져 비교한다. 나아지지 않았으면 되돌리기를 제안한다. 되돌릴지는 사용자가 정한다.
- **Spec**은 «동작이 바뀌지 않았나»를 본다. Spec 브리프에 이 물음을 더한다.
- **Standards**와 Door 판정은 그대로다.

## 왜 축을 나누나

한 변경이 한 축은 통과하고 다른 축은 떨어질 수 있다.

- 모든 표준을 따르지만 엉뚱한 것을 구현한 코드 → **Standards 통과, Spec 실패.**
- 이슈가 요구한 그대로 하지만 프로젝트의 관례를 깨는 코드 → **Spec 통과, Standards 실패.**
- 표준도 따르고 요구한 그대로 하지만 다른 호출자를 깨거나 보안 구멍을 여는 코드 → **Standards · Spec 통과, Correctness 실패.**

따로 보고해야 한 축이 다른 축을 가리지 않는다.
